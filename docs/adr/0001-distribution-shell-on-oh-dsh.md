# 0001 发行版外壳：以 oh-dsh 为基座的源码级 fork

Status: accepted

## 决策

整合包（"傻瓜包"）是**发行版外壳**——在基座之上组合安装器、启动器、精选插件与预设配置，让 Windows 小白开箱即用三种界面（webui/gui/tui）。基座选定 **oh-dsh**（社区发行层：三形态统一、固定版本 DSH runtime、分层分发），实现方式为**一次性源码级 fork 并独立演进**：copy 其仓库后删删改改，不与上游合并（用户明确：开源项目 copy 下来即归自己，上游更新与本项目无关）。DSH/oh-dsh 版本**锁定基线**，升级由整合包自己掌控。插件许可政策**宽松**（侵删兜底）。插件集合按"每功能一实现"收敛为核心包（默认启用）+ 可选包（默认关）两层。

## 背景

用户目标是"供大家开箱即用的傻瓜整合包"：追求轻量化（功能唯一性 > 资源开销 > 包体积）、去重、兼容性修复。调研 50 个社区仓库后发现 oh-dsh 已实现三形态统一发行层（同一 ohdsh CLI + Pinned runtime + 共享数据、独立 Profile），且非 DSH 内核 fork——正是"发行版外壳"模式的现成骨架。站在其肩上可省去 Electron 壳、TUI 集成、安装器与自动更新的重复劳动，把精力集中在选品、去重、补丁与傻瓜化。oh-dsh 内置 marketplace（@oh-dsh/plugin-marketplace），故不再安装独立插件市场（dsh-market 已从选品中移除）。

## 考虑过的方案

- **官方 DSH 自建发行层**：全部自己搭，控制力最强，但 Electron/TUI/安装器重复造轮子，被否决。
- **构建时 vendoring**（仓库只存配方，CI 拉取固定版本叠加）：跟上游冲突最小，被用户否决——用户选择直接 copy 仓库、删删改改，独立演进。
- **持续跟踪上游合并**（常规 fork 模式）：被用户否决——开源 copy 下来即归自己，上游更新不跟进。
- **配方清单+脚本**：不够"开箱即用"，被否决。

## 后果

- **基线冻结**：一次性 copy 后不再合上游，oh-dsh/DSH/各插件的上游修复、安全更新与新特性不再自动进入（与 Q8 锁定基线策略一致，升级完全由整合包发版驱动；如未来确需上游修复，选择性 cherry-pick）。
- **生态风险**：全部插件诞生于 2026-08 一周内，无长期维护记录；基座与入选插件的质量以我们 copy 时点的状态为准，需持续观察并自担修复。
- **自维护义务**：凡是上游修过而我们冻结线也有的 bug，只能自己补丁（补丁簿）。
- **版本锁定**：所有补丁针对锁定基线编写。
